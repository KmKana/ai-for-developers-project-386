# Запись на звонок (Call Booking)

Упрощённый сервис бронирования времени по мотивам [Cal.com](https://cal.com): владелец публикует типы встреч и доступное время, а другой человек выбирает свободный слот и записывается на звонок.

В проекте нет авторизации, личных кабинетов, интеграций с внешними календарями и уведомлений — функциональность намеренно ограничена, чтобы сосредоточиться на главном.

## Сценарий (по референсу Cal.com)

### Путь владельца

1. Владелец открывает раздел **«Типы встреч»** и создаёт новый тип: задаёт название (например, «Знакомство»), описание («Короткий созвон: знакомимся и обсуждаем задачу») и длительность (например, 30 минут).
2. Созданный тип появляется в каталоге и сразу становится доступен гостям на странице записи.
3. Чтобы увидеть результат, владелец открывает раздел **«Предстоящие встречи»**: там появляется список записей гостей по всем типам встреч, отсортированный по времени — сначала ближайшие. После того как гость записался, встреча видна в этом списке сразу.

### Путь гостя

1. Гость открывает главную страницу — видит описание сервиса и кнопку «Записаться на встречу». Каталог типов встреч открывается отдельно, по адресу `/catalog`: там видны название, длительность и описание каждого типа.
2. В каталоге выбирает тип встречи, например «Знакомство, 30 минут».
3. Открывается календарь на ближайшие **14 дней** (начиная с завтрашнего дня; выходные недоступны).
4. Выбирает день — приложение показывает свободные слоты этого дня. Начало каждого слота стоит на 30-минутной сетке, а длительность слота равна длительности выбранного типа встречи.
5. Выбирает свободный слот и заполняет форму: имя и email.
6. Подтверждает запись — слот занят, это время больше никому недоступно. Если слот успел занять кто-то другой, гость видит сообщение и выбирает другое время.
7. Созданная встреча сразу появляется в списке предстоящих встреч владельца.

> На первой итерации главная страница статична и не обращается к API, а кнопка ведёт на заглушку `/booking`. Календарь и полноценное бронирование реализуются следующим этапом — см. `docs/adr/0001-home-page-scope.md`.

## Правила и ограничения приложения

- Владелец календаря один и задан заранее (`Kanybek`); регистрация не нужна ни владельцу, ни гостю.
- Часовой пояс владельца: `Asia/Almaty`. Рабочие часы: понедельник–пятница, 09:00–18:00.
- Окно записи занимает 14 календарных дней, начинается с завтрашнего дня и сдвигается со временем.
- Шаг доступных стартов: 30 минут. Длительность слота совпадает с длительностью выбранного типа встречи (от 5 до 480 минут).
- Одно и то же время нельзя занять дважды, даже разными типами встреч; частичное наложение интервалов запрещено. Следующая встреча может начинаться в момент окончания предыдущей.
- Правило действует и для двух запросов, пришедших одновременно: успешным будет только один, второй получит ответ «время недоступно». Атомарность обеспечивается `synchronized` внутри одного экземпляра Spring Boot; проект рассчитан на один процесс. Распределённые блокировки и многопроцессная синхронизация не реализованы.
- Данные хранятся в памяти процесса: **перезапуск сервиса сбрасывает** созданные типы встреч и записи.
- Регистрация, внешние календари и уведомления не входят в проект.

## Стек и генерация клиента

- **Бэкенд:** Java 21, Spring Boot 3 (Maven). Хранение данных — в памяти процесса.
- **Фронтенд:** React 18, TypeScript, Vite.
- **Контракт API** описан на TypeSpec (`api/tsp/main.tsp`).
- Из контракта генерируется **OpenAPI-спецификация** (`api/openapi/openapi.yaml`).
- Из спецификации генерируется **клиентский SDK** для фронтенда (`frontend/src/sdk`), им пользуется весь код фронтенда — URL и типы ответов нигде не дублируются вручную.

Команды генерации (нужны только при изменении контракта):

```bash
cd api/tsp && npm install && npm run generate     # TypeSpec -> OpenAPI: api/openapi/openapi.yaml
cd ../../frontend && npm install && npm run generate-sdk   # OpenAPI -> SDK: frontend/src/sdk
```

## Каркас, проверки и CI

- Версии инструментов зафиксированы в `mise.toml` ([mise](https://mise.jdx.dev): Java 21, Maven 3.9.6, Node 24). После установки mise: `mise install` и `mise run install`.
- Одна команда всех проверок — **`mise run check`**: Spotless (формат Java), ESLint и Prettier (фронтенд), тесты бэкенда (JUnit 5, включая контрактные и тест конкурентности), Vitest, проверка типов и сборка React, проверка расхождения OpenAPI/SDK и браузерный E2E. проверка расхождения контракта и Spotless идут параллельно, Vitest запускается после JUnit и сборки и не страдает от конкуренции за CPU, E2E запускается последним: если предыдущая проверка упала, серверы E2E не поднимаются.
- На каждый push отдельный workflow `.github/workflows/check.yml` запускает ту же команду `mise run check` с теми же версиями инструментов из `mise.toml`. Workflow `.github/workflows/hexlet-check.yml` создан Hexlet и не редактируется; релизный workflow также остаётся отдельным.
- Дымовой тест запуска приложения — `SmokeTest` (бэкенд поднимается и отвечает 200).
- Git-хуки: `mise run hooks` включает pre-commit из `.githooks/` (прогон линтеров перед коммитом).
- Dev-серверы можно держать фоном через daemons mise (`mise run backend` / `mise run frontend`, либо `mise daemons start backend frontend`) — нужен experimental-режим и pitchfork, см. `mise.toml`.
- Рабочие правила для агентов и формат коммитов — в `AGENTS.md`: коммиты по Conventional Commits (`feat:`, `fix:`, `chore:`, …).

## Как запустить

Через mise (порты 8080 и 5173, два терминала или daemons):

```bash
mise run backend     # бэкенд: Spring Boot
mise run frontend    # фронтенд: Vite, запросы /api проксируются на :8080
```

Без mise:

```bash
cd backend
./mvnw spring-boot:run
```

```bash
cd frontend
npm install
npm run dev
```

Тесты бэкенда (включая проверку пересечений и одновременных запросов):

```bash
cd backend && mvn test
```

Тесты фронтенда (главная страница и переход к записи):

```bash
cd frontend && npm test
```

Браузерный E2E (`mise run test-e2e` или `cd frontend && npm run test:e2e`) поднимает **настоящие**
Spring Boot и Vite на отдельных портах: бэкенд `18080`, фронтенд `15173`. Dev-серверы на
`8080`/`5173` не затрагиваются. Playwright ждёт готовность обоих серверов, открывает
установленный Chrome (`channel: 'chrome'`, `C:\Program Files\Google\Chrome\Application\chrome.exe`;
скачивание браузера не требуется) и останавливает серверы после теста — при успехе и при падении.
В CI используется образ `ubuntu-24.04`, где Google Chrome предустановлен; наличие браузера
проверяется шагом `google-chrome --version` перед прогоном проверок.

Адрес бэкенда для прокси Vite задаётся переменной `VITE_API_PROXY_TARGET`; по умолчанию dev
проксирует `/api` на `http://localhost:8080`. Порты можно переопределить переменными
`E2E_BACKEND_PORT` и `E2E_FRONTEND_PORT`. Ответы API в E2E не подменяются: все запросы идут через
реальные серверы, данные изолированы свежим процессом бэкенда на каждый прогон. Команда
`test-e2e` — финальный шаг `mise run check`; при падении любой предыдущей проверки браузерный
E2E не запускается.

## API (кратко)

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/meeting-types` | Каталог типов встреч |
| POST | `/api/meeting-types` | Создать тип встречи (владелец) |
| GET | `/api/slots?meetingTypeId=…` | Свободные слоты типа на ближайшие 14 дней |
| POST | `/api/bookings` | Записаться на свободный слот |
| GET | `/api/bookings` | Предстоящие встречи владельца (все типы) |

Ошибки: `400` — некорректные данные запроса (пустое название, длительность вне диапазона, неизвестный тип встречи, неверный email); `409` — время недоступно (слот занят, пересечение с другой встречей, старт вне 30-минутной сетки, вне рабочего дня/часов или окна записи). Полный контракт — в `api/openapi/openapi.yaml`.
